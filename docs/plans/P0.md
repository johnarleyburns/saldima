## Risks and open questions

- **XML-canonical + encrypted R2 storage landed (supersedes storage in
  SPEC/DESIGN).** `docs/architecture/TECHNICAL-DESIGN.md`'s Phase 1-2 is
  done: `Book` no longer has an `accounts`/`transactions`/`splits` SQLite
  schema at all. `GncXmlDocument` (via the new `BookXmlStore`) is the live,
  in-memory accounting model, loaded from and saved to R2 as a gzip'd,
  **AES-256-GCM-encrypted** object (key derived from `MASTER_KEY` + tenant
  via HKDF, mirroring the existing TOTP-secret encryption) — the server
  never holds plaintext book bytes at rest, only in the DO's working memory
  while a request is in flight. Every save writes a _new_ version
  (`tenants/<tenantId>/books/<bookId>/<timestamp>-<nonce>.gnucash.gz.enc`)
  rather than overwriting, pruned to the most recent 30 versions, so earlier
  versions are real rollback backups. This is **not yet** the zero-knowledge
  design (Phase 4): the key is server-derived, not client-held, and there is
  no separate client-side "download, edit locally, explicit save" flow — the
  DO's in-memory copy plays that role today, and every mutation saves
  immediately (the de facto always-on auto-save). `gcw_*` tables (users,
  sessions, TOTP, staged bank-import batches) are unaffected. Verified with
  the full local suite against real DO/R2 bindings
  (`pnpm test:runtime`, 12/12) and the full Playwright e2e suite against the
  real dev server (`pnpm e2e`, 18/18 on Chromium-based projects; WebKit/
  Firefox binaries were not installed in the sandbox this landed in, so
  those two browser projects are unverified here, not failing).
  Zero-knowledge client-side encryption, cloud snapshot-DAG sync and
  multi-device reconciliation (Phase 4+) stay deferred to a later milestone.
- **Zero-knowledge vault, Milestone 1 landed (#88/#89/#90/#91).** A fully
  additive, opt-in path now exists alongside the server-held-key storage
  above, not replacing it: `packages/crypto` (key hierarchy), a client-side
  JS bundle (`apps/web/src/client/vault.ts`, built by `pnpm build:client`
  and served by Workers Assets), and `/app/vault/*` routes that only ever
  see ciphertext (`vault-store.ts`). A user can set up a vault (DEK wrapped
  under a passphrase-derived KEK and a recovery-code-derived KEK, recovery
  code shown once), back up their book now (client-side AES-GCM encryption
  of the existing lossless XML export, uploaded as opaque bytes), and
  verify a backup (unwrap with either the passphrase or the recovery code,
  decrypt, byte-compare). `e2e/vault-setup.spec.ts` asserts the raw
  passphrase/recovery code never appear in any request body. **This is
  backup/verify only** — no existing book-editing route is touched, there
  is no live client-side editing flow yet, and the key is not used for
  anything but this vault's own snapshots. Full client-side editing,
  multi-device key distribution and the snapshot-DAG merge protocol are
  still Milestone 2+, not started.
- **Proton as an EU storage backend: researched, not pursued.** The owner
  asked about storing EU tenants' encrypted books with Proton instead of
  Cloudflare R2. Proton has no S3-compatible or otherwise documented API for
  third-party storage integration (Proton Drive is client-only), and its ToS
  bars the kind of bulk, non-human automated access a multi-tenant SaaS
  backend would need — building on its unofficial internal API would be a
  ToS violation and an operational risk. Recommendation instead: Cloudflare
  R2's native EU "Jurisdictional Restrictions" (an `eu`-jurisdiction bucket,
  fixed at creation, no new vendor) likely satisfies "data stays in the EU"
  outright; if a tenant specifically objects to Cloudflare as a company, a
  real S3-compatible EU/Swiss provider (Exoscale or Infomaniak) could be
  added later behind the same `R2BucketLike`-shaped interface `BookXmlStore`
  already uses. Not built in this pass; recorded here if it comes up again.
- **Design/GTM docs are now in hand.** The Design tab confirms the target
  `worker/edge/book` layout, `gnucash-file`/`api-contract` packages and the
  `/api/v1` routes; P1 restructures P0's minimal `index.ts`/`app.ts` into it.
  The Go-to-market doc adds the no-analytics, source-offer and launch-sequence
  constraints recorded in `CLAUDE.md`.
- **ESLint vs Biome.** The P0 backlog says "ESLint rules"; the CI table says
  Biome. Decision: Biome for lint/format plus small TypeScript-AST gates for the
  money/random/clock rules, so the rules are enforced without maintaining two
  linters. Revisit if the Design tab specifies otherwise.
- **Spike fixture.** Without the owner's real book, only synthetic fixtures can
  run; the real-GnuCash oracle acceptance cannot pass. Issue #6 stays blocked.
- **Cloudflare Containers in local dev.** `pnpm dev` needs Docker for the
  converter. The smoke suite must pass without the converter (XML path marked
  as a runtime test) until the container image exists.
- **Action pinning.** Actions are pinned to commit SHAs; Dependabot keeps them
  current. First pins are recorded in `ci.yml`.
- **Money fixtures are rule-derived for now.** Half-even cases come from
  GnuCash's documented currency rounding, not yet from the owner's real book.
  P0-5 must replay the same primitives against the fixture and the oracle.
- **Contract coverage is staged.** Clock, ID, random, KV and R2 contracts run
  against fake and real implementations now. Book, Converter and Stripe real
  contract suites arrive with those adapters (P0-5, P0-6, P1); Stripe's is
  nightly in test mode as the spec requires. Issue #4 tracks this.
- **License scan scope.** The gate scans production dependencies with a strict
  MIT/BSD/Apache/ISC/0BSD/CC0 allowlist. Dev tooling is excluded because it never
  ships; Vite currently pulls MPL-2.0 `lightningcss` into the test runner. This
  is recorded here rather than silently allowlisted; revisit before the App
  Store build (P5).
