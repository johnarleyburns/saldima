# P2 — Book formats, industry templates, and localisation

This phase makes Saldima a serious GnuCash-compatible alternative for real small
businesses on all three tracks:

1. Read **and write** both GnuCash backends — SQLite and XML — like GnuCash
   desktop.
2. Ship **100 industry-sensitive templates** with country-specific accounts.
3. Support the **same language set as GnuCash 5.14**, with AI-generated
   translations that are clearly marked until a human reviews them.

Parity rule: the web, iOS, and Android tracks consume the _same_ fixtures,
template registry, and translation catalogs, pinned by commit. No track invents
its own account names or translations.

## Track 1 — Both file formats

Status: iOS detects SQLite/XML by bytes and reads the XML backend (accounts,
commodities, transactions, splits) in #34; GnuCash 5.14 generated the fixtures
(`fixtures/books/oracle-mini.gnucash`, `oracle-mini.sqlite.gnucash`).

| Capability                            | Web     | iOS  | Android |
| ------------------------------------- | ------- | ---- | ------- |
| Format detection (magic bytes, gzip)  | yes     | done | yes     |
| Read SQLite accounts                  | yes     | done | yes     |
| Read SQLite transactions/splits       | yes     | done | yes     |
| Read XML accounts/transactions        | yes     | done | yes     |
| Write SQLite book                     | —       | done | planned |
| Write XML (gzip) book                 | yes     | yes  | yes     |
| Round-trip equal semantics, both ways | partial | yes  | partial |

All three gzip XML writers were opened and re-saved by GnuCash 5.14 on
2026-11-24. The writers add the structural ROOT first, `trn:date-entered`,
valid split GUIDs and `split:reconciled-state`, which the desktop requires.

Rules:

- Never trust the extension; sniff bytes (`SQLite format 3`, `1f 8b` gzip,
  `<?xml`).
- Preserve unknown elements, slots, and KVP; do not drop what we do not model.
- Amounts stay exact rationals; XML `num/denom` maps to `Money` without floats.
- The oracle is GnuCash 5.14 (`gnucash-cli` / Python bindings locally); every
  fixture is opened and re-saved by it before it is committed.

## Track 2 — 100 industry templates and country packs

### Model

A template is **industry chart × country overlay × locale presentation**:

```json
{
  "id": "us-dental-practice",
  "industry": "dental-practice",
  "country": "US",
  "currency": "USD",
  "base": "professional-services",
  "accounts": [
    { "key": "assets.cash", "name": "Cash", "type": "CASH", "parent": null },
    {
      "key": "income.treatment",
      "name": "Patient Treatment Income",
      "type": "INCOME",
      "parent": "income"
    }
  ],
  "taxNotes": ["Sales tax generally not charged on dental services."],
  "reviewer": { "kind": "cpa", "name": null, "reviewedAt": null }
}
```

- `key` is a stable machine identifier; stored account names come from the
  English source and **are never rewritten by translation** (display-only), so
  books stay portable and merges stay stable.
- Country overlay adds/replaces accounts and notes: VAT/GST/sales-tax payable,
  payroll withholdings, pension/superannuation, local equity and year-end names.
- Every template validates against `registry.schema.json`: unique keys, valid
  GnuCash types, no orphan parents, exactly one root per type family, no empty
  names, ≤ 200 characters.

## Track 3 — Localisation (GnuCash's language set)

GnuCash 5.14 ships these 55 locales (from `/usr/share/locale/*/LC_MESSAGES/gnucash.mo`):

```
ar as az bg brx ca cs da de doi el en_AU en_GB en_NZ es es_NI et eu fa fi fr
gu he hi hr hu id it ja kn ko kok kok@latin ks lt lv mai mk mni mni@bengali mr
nb ne nl pl pt pt_BR ro ru rw sk sr sv ta te tr uk ur vi zh_CN zh_TW
```

### Catalog rules

- Source strings are our own English (`en`), authored in the registry and UI.
- Catalogs are JSON keyed by stable message id:
  `{ "msgid": "account.treatment_income", "msgstr": "...", "machine": true, "reviewedBy": null }`.
- **AI-generated translations are allowed but must say so**: `machine: true`
  until a native reviewer sets `reviewedBy`; the UI may show "machine
  translation" in About/Settings, and release notes list unreviewed locales.
- Never copy GnuCash `.po` text (GPL). Translations are generated from our own
  strings only.
- Stored book data is never localised: account names stay English in the file;
  the UI overlays translations by `key`. Changing UI language never touches a
  book.
- Glossary of accounting terms is shared across catalogs (e.g. Assets, Equity,
  Accounts Receivable, Retained Earnings) so translations stay consistent.
- Tests: every catalog has every key; no empty strings; placeholders match;
  RTL locales render; fallback to `en` on missing keys; catalogs compile into
  Swift and Kotlin resources at build time.

### Rollout

1. `en` source + `en_GB`, `en_AU`, `en_NZ`, `es`, `fr`, `de`, `pt_BR`, `zh_CN`.
2. Remaining GnuCash locales generated, marked machine, then reviewed in
   batches of ten.
3. Language picker on web and both apps; per-device override stored locally.
